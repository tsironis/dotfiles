Design summary · journeys through the system

A personal assistant, wrapped in a TUI

Five journeys through one shared core: how a todo gets triaged, how a proposal becomes a filed artifact, how a monthly goal rolls up against everything else, how a spawned Claude Code session earns its keep, and how the whole thing gets built.

Summarizing docs/unified-tracker/design.md — a design, not code, most of it gated behind the 2026-10-07 Linear trial checkpoint or opportunistic timing.

§0

Shape: a shared core, two surfaces

A single Go core implements the todo, artifact, goal, and people logic as a library. Interaction code depends on trait shapes — TodoBackend and its siblings — never on one storage mechanism directly. Two surfaces sit on that core, and every journey below runs through one of them.

flowchart TB
    Core["Go core library\nTodoBackend / Artifact / Goal / People traits"]
    Core --> TUI["TUI — bubbletea\nprimary, everyday interface"]
    Core --> CLI["CLI\nfuture agents layer, scripting\noutput format still open"]

    TUI --> D1["§1 Tasks"]
    TUI --> D2["§2 Artifacts"]
    TUI --> D3["§3 Goals / State"]
    TUI --> D4["§4 Reasoning"]
    TUI --> D5["§5 People / Resources"]

01 · §1

Journey: capturing and closing a task

Carried over from docs/unified-tracker/linear-trial.md's appendix: weekly ISO cycles with rollover, fzf-driven triage. Only the build trigger changed — the trait plus LocalYamlBackend ships regardless of the Linear trial's outcome, since the TUI needs it either way.

flowchart LR
    Start(["Open TUI"]) --> Browse["Browse todos\ncurrent ISO week"]
    Browse --> Add["Add todo"]
    Browse --> Triage["fzf-driven triage"]
    Add --> Store[("todos.yaml\nLocalYamlBackend")]
    Triage --> Complete["Mark complete"]
    Triage --> Rollover{"End of week,\nstill open?"}
    Rollover -- yes --> NextWeek["Rolls into\nnext ISO week"]
    Rollover -- no --> Done(["Closed"])
    Complete --> Store
    NextWeek --> Store
    Store --> Git[("git commit\nthis repo")]
backend LocalYamlBackend file todo/todos.yaml storage git-native, atomic commits future LinearBackend — optional, same trait

Not a hard gate. The original design waited on the Linear trial before building anything. The trait abstraction removes that: a LinearBackend becomes optional future work, only if the trial calls for it.

02 · §2

Journey: filing an artifact

Adapts proposal-agentic-artifact-registry.md's frontmatter-as-registry pattern, scaled down for solo use — no merge-time numbering ceremony, since one person filing alone can't collide with themself. The storage location changes from the original design though: Obsidian becomes the primary home for every personal artifact, not files scanned in place inside each project's repo.

flowchart LR
    Draft(["Have a PoC, proposal,\nor research draft"]) --> New["new <type> <project> <slug>"]
    New --> File["Filed in the vault\nProjects/<name>/ or Notes/"]
    File --> FM["Frontmatter set:\nid, type, project [[wikilink]],\nstatus: draft, created"]
    FM --> Edit["Edited in Obsidian\ndesktop or mobile capture"]
    Edit --> Status{"Status advances\nper type"}
    Status --> Index["Core walks vault frontmatter\nlist / show / stale — generated, never hand-kept"]
identity filename is id — no second identifier sync Obsidian's own sync, not git layout Projects/<name>/<name>.md index note fallback Notes/ for project: null
TypeStatus vocabulary
proposaldraft → proposed → accepted
researchdraft → proposed → concluded
tool-docdraft → proposed → published
pocdraft → filed
session-notefiled — no gate, just needs to be findable

Migration is opportunistic, not blocking. Existing artifacts scattered across project repos and the old docs/notes/ fallback move into the vault eventually — cleanup, not a prerequisite for anything else here.

03 · §3

Journey: setting a goal, watching it roll up

"Where am I, where am I heading" — bullet-journal yearly and monthly goals, rolled up deterministically against tasks, artifacts, and people. No LLM in this step; the reasoning layer (§4) is a separate, deliberate trigger.

flowchart LR
    SetY["Set yearly theme\ngoals.yaml: yearly"] --> SetM["Set monthly goal\ntitle, month, parent_theme, project"]
    SetM --> Active["status: active"]
    Active --> Rollup["Rollup function\ngoals.yaml + todos + artifacts\n+ projects.yaml + people"]
    Rollup --> View["TUI renders:\nprogress per goal, open items per project,\nstale artifacts"]
    View --> Review{"Reviewed\nat month end"}
    Review -- met --> DoneG["status: done"]
    Review -- abandoned --> Dropped["status: dropped"]
    Review -- unfinished --> Carried["status: carried\nauto-rolls to next month"]
file goals.yaml engine Go core function, not a standalone script doubles as context handed to a spawned Claude Code session

carried makes the bullet-journal migration ritual an explicit status instead of a manual copy-paste into next month's page.

04 · §4

Journey: spawning a reasoning session

The TUI triggers real Claude Code sessions as child processes rather than reimplementing reasoning itself. Two modes, chosen per task — and nothing a session produces is filed automatically.

flowchart LR
    Trigger(["Triggered on a goal,\nrollup, or artifact"]) --> Mode{"Choose mode"}
    Mode -- quick summary --> Headless["Headless\nclaude -p '...'\ncapture stdout, render inline"]
    Mode -- open-ended review --> Interactive["Interactive handoff\nsuspend TUI screen\nexec claude interactively"]
    Interactive --> Resume["TUI resumes on exit\nsame pattern as lazygit + $EDITOR"]
    Headless --> Output["Session output shown in TUI"]
    Resume --> Output
    Output --> Gate{"User reviews,\nkeybind to save?"}
    Gate -- yes --> Save["Saved as session-note artifact"]
    Gate -- no --> Discard(["Discarded — nothing auto-filed"])
    Save -.-> Vault[("Obsidian vault")]
headless claude -p, no screen handoff interactive suspend / exec / resume gate human decides what's worth finding P2 idea pipe through lege for a TTS review pass
05 · §5

Journey: logging a person or resource

No longer gated on "artifacts and todo proving insufficient first" — builds alongside artifacts and goals, since a people/resources view is cheap enough in a TUI that deferring it doesn't buy much.

flowchart LR
    Add(["Add in TUI"]) --> Which{"Person or\nresource?"}
    Which -- person --> Person["people.yaml\nname, context, relation,\nnotes, last_contact"]
    Which -- resource --> Resource["resources.yaml\nname, type, owner,\nnotes, url"]
    Person --> Feed["Feeds the §3 rollup\ne.g. a collaborator tied to a project"]
    Resource --> Feed
shape flat YAML, same family as projects.yaml storage git-native
