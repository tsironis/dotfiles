# Claude instructions

These are my global instructions and they apply to every project. Project-level
CLAUDE.md files add to them rather than replace them.

## Planning discipline

Before writing any code, ask me open questions one at a time to establish scope
and approach. Flag assumptions rather than resolving them silently. Once we
agree on a plan, wait for my explicit approval before proceeding.

## Writing style

These rules apply to everything you write for me, including chat replies,
commit messages and code comments.

- First, define the structure of the text, based on the type of document being
  written, and potential conventions that may accompany it. Then expand this
  structure to prose.
- Reduce the em dashes, to an absolute minimum.
- Avoid the use of "It's not X but Y" pattern
- Avoid writing with semicolons or colons to make a point.
- Ensure every paragraph focuses on a single idea using a clear topic sentence,
  2–4 supporting sentences, and a concluding transition, breaking to a new
  paragraph if it exceeds 5 sentences or shifts focus. This help guide the
  reader and make your point more clear.
- Avoid lingo such as "gate", "surface", "gate the surfaces", "load-bearing",
  "wired up", "blast radius", "Substrate" / "Spine" / "Seams" etc.

## Technical documents

These rules apply on top of the writing style above whenever the output is a
document, such as a README, a design note, a runbook or a postmortem.

- Use inclusive language.
- Use active voice. Say "the authority closed the mine" rather than "the mine
  had to be closed by the authority". Keep passive constructions to the cases
  where the actor is unknown or genuinely irrelevant.
- Keep sentences to an average of 15 to 20 words, varying short and long ones
  deliberately. Stick to one main idea per sentence, plus at most one related
  point.
- Avoid nominalizations. Prefer the verb the abstract noun was built from, so
  "validates the payload" rather than "performs a validation of the payload",
  and "we discussed the matter" rather than "we had a discussion about the
  matter".
- Write instructions as imperatives. "Remove the packet from the box" rather
  than "the packet should be removed from the box".
- Order documents that describe a process or a sequence of events
  chronologically, such as runbooks, postmortems, migration notes and
  changelogs. Order reference documents by what the reader needs first instead,
  such as READMEs, API docs and architecture decision records.
- Start at a single H1, respect heading order and do not skip levels.
- Follow every heading with text before the next heading. Never stack one
  heading directly onto another.

## Commit and pull requests

Do not add Claude Code, Anthropic, or Opus insignia. Do not add "generated by"
or "co-authored by" notes in MRs and commit messages.

## PDF handling

For text-based PDFs, extract text with the local `read-pdf` tool (via Bash)
instead of reading the PDF directly. `read-pdf <file.pdf>` prints the extracted
text to stdout, `read-pdf --pages START-END <file.pdf>` limits it to a page
range, and `read-pdf --annots <file.pdf>` also prints annotation/comment text
(sticky notes, highlights). This avoids the token cost of parsing each page as
an image.

If `read-pdf` returns little or no text, the PDF is scanned or image-only, so
fall back to reading it directly (page-image parsing) instead.
